# M8.8 Normative Revision — 2026-08-28

Status: COMPLETE
Applies to: specs/pre-playtest-integrity/spec.md
Audited baseline: main@95606565c44b7bab04e434856ad9cd65dbefd101

This revision is normative. Existing S1-S21 remain in force except where this file is stricter.

## S22 — Required CI must be green

The executor MUST treat the current domain-tests workflow as failed while any required job is red.

The real-hook guard suite MUST pass all scenarios. Negative hook tests MUST prove the intended rejection reason/path rather than accepting any generic preflight failure as success.

The executor MUST NOT weaken repository identity, lost-update protection, or transport isolation merely to make fixtures green.

## S23 — Store-compliant Android target

The Android build path MUST target Android 16 / API 36 or later for new-app/update submission readiness under the 2026-08-31 Google Play requirement.

The target SDK value MUST be verified in the generated build evidence, not only in source text.

The executor MUST preserve intentional minSdk compatibility unless a measured/API requirement forces a change.

The API-level change MUST receive Android 16 lifecycle and permission regression coverage.

## S24 — Resolved Unity dependency/project state is reproducible

A device/release-ready source state SHOULD include editor-generated Packages/packages-lock.json when Unity resolves packages.

Canonical ProjectSettings and render-pipeline assets required to reproduce the certified build MUST be tracked or their deterministic generation MUST be proven and bound to evidence.

The executor MUST NOT manually invent opaque Unity YAML/serialized assets to satisfy this requirement.

A second clean checkout of the resulting source MUST be able to reach the same semantic compile/build state without unexplained tracked mutation.

## S25 — iOS has a reproducible build-certification path

Before the MVP can be called fully production-ready, the repository MUST contain a repeatable iOS Xcode-generation/build-certification path.

It MUST bind at least:
- source SHA and dirty state;
- Unity editor identity;
- deterministic bundle identifier/project configuration;
- generated Xcode output identity;
- Xcode version and SDK version when built;
- CoreMotion/NSMotionUsageDescription evidence;
- build/sign/install result when credentials/device are genuinely available.

Provisioning credentials and signing secrets MUST NOT be committed.

## S26 — Current Apple submission toolchain is respected

Any App Store readiness claim made under this campaign MUST use Xcode 26 or later and iOS 26 SDK or later, matching the requirement effective 2026-04-28.

If that toolchain is unavailable, iOS store readiness remains UNVERIFIED.

## S27 — Performance, UX, and accessibility claims require real evidence

The executor MUST NOT declare full production readiness from headless tests alone.

Where suitable hardware exists, final certification MUST include:
- Builder and Explore frame-time sanity;
- region transition timing;
- Expedition battery/thermal sanity;
- touch/readability/safe-area checks;
- a basic accessibility review appropriate to the actual supported UI technology.

Unavailable physical tiers MUST be labeled UNVERIFIED.

## S28 — Final project-completion claim

M8.8 COMPLETE means all locally executable requirements are closed and no known P0/P1 blocker remains.

FULL MVP PRODUCTION-CERTIFIED is a stronger claim and additionally requires genuine Android and iOS build/device evidence, reproducible project state, current store toolchains, and measured user-facing performance/UX gates.

The executor MUST keep these claims separate.
